# ADR-0015: Audit Tracing and Operational Logging

## Status

**Proposed** — 2026-05-26

## Context

Auto Core Platform is becoming an enterprise ERP platform for financial, inventory, procurement, sales, and workshop operations. In this domain, "logging" is overloaded and currently risks mixing two very different responsibilities:

1. **Audit tracing — the business and compliance layer.** Users, accountants, support staff, and future auditors need to answer: who changed this invoice price, when did they change it, what did the row look like before, and what did it look like after? This record must be persisted in the database and protected from ordinary deletion.
2. **Operational logging — the developer and operations layer.** Engineers need to diagnose server errors, API latency, failed integrations, WebSocket disconnects, and unexpected runtime behavior. These logs are emitted to the runtime log sink, are filtered by severity, and must not become the accounting source of truth.

Existing ACP architecture already contains adjacent patterns:

- ADR-0001 establishes Prisma `$extends` as an accepted mechanism for global write interception.
- ADR-0002 establishes ledger-style traceability for inventory stock movements.
- ADR-0005 acknowledges that hard deletion audit trails are currently a gap.
- ADR-0010 requires OpenAPI regeneration when new administrative endpoints are added.
- ADR-0013 requires strict tenant isolation for every tenant-owned record and query.

We need an architecture that gives business users durable audit trails without forcing every NestJS service to remember manual audit writes, while also giving engineers adjustable runtime log verbosity without flooding production logs.

## Decision

We will implement **two separate logging systems with separate storage, audiences, retention expectations, and security controls**:

| Layer | Audience | Storage | Purpose | Retention expectation |
|-------|----------|---------|---------|-----------------------|
| Audit tracing | Users, accountants, support, auditors | PostgreSQL `AuditLog` ledger table | Business mutation history with before/after state | Durable business record; no user-facing delete |
| Operational logging | Developers and operators | NestJS logger output / platform log sink | Runtime diagnostics, latency, errors, connection events | Managed by infrastructure log retention |

These two layers must not be treated as substitutes. Operational logs are not audit evidence. Audit records are not a debug log stream.

### 1. Database-Level Audit Tracing

ACP will introduce a centralized, append-only `AuditLog` ledger table and a global Prisma Client Extension that intercepts audited write operations.

Conceptual flow:

```text
[ Client Request ]
        |
        v
[ NestJS Guard + Request Context ]
        |
        v
[ NestJS Service ]
        |
        v
[ Prisma Audit Extension ] -- reads old row --> computes before/after diff
        |
        v
[ Business Mutation + AuditLog Insert ] -- one atomic database commit
```

#### AuditLog record content

Each audit record must capture enough information to reconstruct the business mutation without querying the current version of the entity:

| Field group | Required content |
|-------------|------------------|
| Identity | `id`, `tenant_id`, `entity_type`, `entity_id`, `action` |
| Actor | authenticated user ID / Firebase UID, email if available, role, actor type (`USER`, `SYSTEM`, `MIGRATION`) |
| Request context | request ID / correlation ID, source (`API`, `JOB`, `SCRIPT`), IP address, user agent where available |
| Data snapshots | JSON `before` snapshot, JSON `after` snapshot, JSON `diff`, changed field names |
| Timing | `occurred_at` generated by the server/database |
| Safety metadata | redacted field list, optional reason/comment when supplied by a business flow |

`tenant_id` is mandatory for tenant-scoped business mutations. The audit extension must never trust tenant identity supplied by the request body; tenant context comes from the authenticated request context established by ADR-0013. Background jobs must explicitly run with a system actor context.

Platform-level administrative audit events, if required later, should be handled by a separate Feature Spec. The default `AuditLog` scope in this ADR is tenant business data.

#### Audited operations

Initial audit tracing applies to **updates and deletes** on tenant-scoped business models. This directly addresses high-risk ERP questions such as:

- invoice or purchase bill values changed before finalization,
- workshop task line items removed,
- customer, vendor, vehicle, or catalog master data changed,
- draft transactional documents deleted where deletion is allowed by policy.

Create operations are not part of the initial default audit scope because the created row is the first persisted state. If a feature needs explicit creation provenance beyond `createdAt` and ownership fields, that feature must opt in through its Feature Spec.

New tenant-scoped business models are audited by default unless their Feature Spec explicitly justifies exclusion. Internal technical models such as `AuditLog` itself must be excluded to prevent recursive audit writes.

#### Diff behavior

For an `update`, the extension reads the row before mutation, runs the mutation, reads or uses the returned row after mutation, computes changed fields, and inserts one audit record containing both snapshots.

For a `delete`, the extension records the row before deletion and stores `after = null`.

For `updateMany` and `deleteMany`, silent aggregate logging is forbidden. The implementation must choose one of these safe behaviors per model:

1. enumerate affected rows and write one audit record per affected row in the same transaction, or
2. reject batch mutation for audited models and require callers to use explicit per-row operations.

This prevents a batch audit record from hiding which exact rows changed.

#### Atomicity requirement

The business mutation and the `AuditLog` insert must commit or roll back together. A mutation that succeeds without its audit record is not acceptable.

If a Prisma Client Extension cannot guarantee same-transaction audit writes for a specific operation shape, that operation shape must be blocked or routed through a transaction-aware helper. The audit architecture must not degrade into best-effort logging.

#### Redaction requirement

Audit tracing needs business data snapshots, but it must not persist secrets. The audit layer must redact known secret-bearing fields before writing snapshots, including passwords, password reset tokens, Firebase tokens, API keys, refresh tokens, access tokens, and raw authorization headers.

Business fields such as prices, quantities, statuses, customer names, vehicle identifiers, and document line items are not redacted by default because they are the audit subject.

#### Deletion and retention

`AuditLog` is an immutable audit ledger. There must be no ordinary API endpoint that updates or deletes audit records. Long-term retention, cold storage, or partition archival may be introduced later, but only through a compliance-focused Feature Spec that preserves auditability.

`docs/deletion-policy.md` must list `AuditLog` as non-deletable.

### 2. Dynamic Operational Logging

ACP will use the standard NestJS logging abstraction for operational logs, controlled by a dynamic effective log level.

Supported levels, from least to most verbose:

| Level | Intended use |
|-------|--------------|
| `error` | Unhandled exceptions, failed jobs, failed critical integrations |
| `warn` | Recoverable problems and suspicious conditions |
| `log` | Normal lifecycle and high-value operational events |
| `debug` | Diagnostic details for active investigation |
| `verbose` | Highly detailed trace information used sparingly |

The `LOG_LEVEL` environment variable is the boot-time default. Production must not default to `debug` or `verbose`.

#### Runtime log-level override

ACP may expose a secure backend endpoint:

```text
PATCH /api/admin/settings/log-level
```

The endpoint changes the effective runtime log level without restarting the container. It must obey the following rules:

- It is restricted to platform administrators or an explicitly approved operations role.
- It validates the requested level against the supported level list.
- It records who changed the level and when, either through the audit layer or an equivalent platform-admin audit trail.
- `debug` and `verbose` overrides must have an expiration time so production cannot be left in noisy mode indefinitely.
- It must not change the audit tracing rules. Audit capture remains always-on for audited business mutations.

For local development and single-instance diagnostics, an in-memory override is acceptable. For production environments with multiple API instances, the override must come from a shared runtime configuration source or a propagation mechanism so instances do not disagree about the effective log level. The implementation Feature Spec must choose the propagation strategy before enabling this endpoint in multi-instance production.

#### Structured operational logs

Operational log entries should be structured consistently enough for filtering in the platform log sink. Request logs should include at least:

- request ID / correlation ID,
- HTTP method and route template,
- status code,
- duration in milliseconds,
- tenant ID and actor ID when available,
- error class and safe error message for failures.

Request and response bodies must not be logged by default. Payload logging requires a narrowly scoped debugging change with redaction and expiration.

## Impact Analysis

| Dimension | Impact |
|-----------|--------|
| Database | Adds `AuditLog` as a tenant-scoped append-only ledger. Requires indexes for tenant/entity/time queries. Optional future partitioning may be needed as the table grows. |
| State machines | Does not create a new business status workflow. It records mutations to existing workflows and must not replace existing atomic transition guards. |
| Deletion policy | `AuditLog` must be added as non-deletable. Existing entity deletion rules remain authoritative. |
| Real-time sync | `AuditLog` should not be added to dashboard real-time entity sync by default; it would create noisy cache invalidation and possible recursion. Future audit viewer screens can use normal query refresh or a dedicated stream. |
| API contract | The log-level endpoint changes the backend API contract and therefore requires OpenAPI and generated frontend type regeneration when implemented. Future audit viewer endpoints also require regeneration. |
| Inventory | Audit tracing does not replace `InventoryTransaction`. Stock changes must still go through the ledger service. Audit records may provide metadata for surrounding document edits, but inventory quantity history remains governed by ADR-0002. |
| Finance | Audit tracing complements invoice snapshotting and fiscal lock enforcement. It must not allow edits to finalized or locked records that existing policies forbid. |
| UX | A future audit viewer must follow list page standards: DataTable, sortable columns, global search, top-right actions, and tenant-safe filtering. No UX change is required for the logging endpoint unless an admin settings screen is added. |
| Testing | Requires integration tests for update/delete audit capture, redaction, tenant isolation, batch operation behavior, immutable audit records, and runtime log-level authorization/expiry. |

## Consequences

### Positive

- **Business-grade traceability:** ACP can answer who changed a business record, when, and what changed.
- **Lower service boilerplate:** Services do not need hand-written audit logic for every ordinary update/delete.
- **Consistency:** A global extension reduces the risk of forgotten audit writes.
- **Clear operational controls:** Engineers can increase runtime verbosity during an incident without redeploying.
- **Separation of concerns:** Business audit records are preserved in the database while developer logs remain in the runtime logging system.

### Negative

- **Additional write overhead:** Audited mutations require pre-read and audit insert work, increasing write latency.
- **Storage growth:** `AuditLog` will grow continuously and will eventually require partitioning or archival planning.
- **Implementation complexity:** Same-transaction audit writes and batch mutation handling are more complex than simple service-level logging.
- **Sensitive-data risk:** Incorrect redaction rules could persist secrets in audit snapshots. Redaction must be tested.
- **Runtime logging security risk:** A dynamic log-level endpoint is powerful and must be tightly authorized and expiring.

### Neutral

- Audit tracing is not a substitute for domain-specific ledgers such as `InventoryTransaction` or immutable invoice snapshots.
- Operational logs are allowed to be ephemeral and infrastructure-managed. They do not need the same retention guarantees as audit records.
- Audit records should not be emitted through the dashboard real-time extension unless a future spec creates a dedicated audit-viewing workflow.

## Alternatives Considered

| Option | Pros | Cons |
|--------|------|------|
| Manual audit writes in every service | Maximum domain control and easy custom messages | High boilerplate, easy to forget, inconsistent coverage, difficult to review at scale |
| PostgreSQL triggers | Strong database-level enforcement and difficult to bypass | Hard to capture authenticated actor/request context, PostgreSQL-specific, opaque errors, harder CI testing |
| Prisma Middleware | Similar interception model | Prisma Middleware is deprecated in favor of Client Extensions |
| Full event sourcing | Complete replayable history of all domain events | Major architectural change, projection complexity, over-engineered for current ACP needs |
| Use operational logs as audit trail | No new database table | Fails business requirements: retention is not guaranteed, before/after snapshots are inconsistent, logs are not tenant-queryable business records |
| Static `LOG_LEVEL` only | Simple and secure | Requires restart/redeploy during incidents and slows production debugging |

## Pragmatic Enforcer Analysis

| Area | Assessment |
|------|------------|
| Necessity score | 9/10 — Enterprise ERP financial and inventory systems require durable auditability and controlled diagnostics. |
| Complexity score | 6/10 — Prisma extension diffing, atomic writes, and dynamic configuration are non-trivial but bounded. |
| Complexity-to-necessity ratio | 0.67 — Complexity is justified by compliance and support needs. |
| Simpler alternative | Keep only static `LOG_LEVEL` and manual service audit writes for the highest-risk entities. |
| Why rejected | Manual audit is likely to miss future services, and static logging slows incident response. However, full event sourcing and hash-chained audit records are deferred as over-engineering. |
| Recommendation | Approve with simplifications: implement update/delete audit first, exclude full event sourcing, require redaction tests, and require expiration for noisy runtime log levels. |

## Validation Criteria

- Updating an audited tenant entity creates exactly one `AuditLog` row with matching `tenant_id`, actor context, `before`, `after`, changed fields, and request ID.
- Deleting an audited entity allowed by `docs/deletion-policy.md` creates an `AuditLog` row with the deleted row in `before` and `after = null`.
- Attempting to update or delete an `AuditLog` record through the application is impossible through ordinary APIs.
- Tenant users can only query audit records for their own tenant when audit viewing APIs are introduced.
- Known secret-bearing fields are redacted in persisted audit snapshots.
- `updateMany` and `deleteMany` on audited models either write one audit row per affected row or are rejected.
- `LOG_LEVEL` sets the boot-time default operational log level.
- Authorized runtime log-level changes take effect without a container restart.
- Unauthorized users cannot change runtime log level.
- `debug` and `verbose` runtime overrides expire and revert to the configured default or previous safe level.
- Adding the log-level endpoint regenerates `apps/core-api/openapi/openapi.json` and `apps/core-web/src/api/generated/openapi.ts`.

## Open Questions for Implementation Spec

1. Should ACP introduce a separate `PlatformAuditLog` for platform administrator actions, or should platform actions be represented in the same audit table with a formally documented scope model?
2. Which shared runtime configuration mechanism should production use for multi-instance log-level propagation: database-backed setting, cache, Pub/Sub, or managed platform configuration?
3. Which entities, if any, require create-operation audit records in the first implementation wave?
4. Should audit records include cryptographic hash chaining now, or defer tamper-evidence beyond database immutability and access controls?
